# Publishing a Vernac Release

This guide describes local Maven Central releases and IntelliJ plugin
distribution through GitHub Releases and JetBrains Marketplace.
It also records the current scope of release automation.

## Release scope

The following components are published to Maven Central:

- `org.vernac:vernac` — parent POM
- `org.vernac:vernac-runtime`
- `org.vernac:vernac-runtime-jdbc`
- `org.vernac:vernac-jdbc-spring-boot-starter`
- `org.vernac:vernac-compiler`
- `org.vernac:vernac-maven-plugin`

The example applications, language server, and IntelliJ plugin are not
published by the command in this guide. Distributing the IntelliJ plugin
is a separate step.

## Prerequisites

- JDK 25 for building the complete repository, including the IntelliJ plugin.
- Maven 3.9.x.
- GnuPG available on `PATH`.
- A signing key whose public part is available on a supported keyserver.
- Access to the verified `org.vernac` namespace in the Central Publisher Portal.
- A Central Portal user token configured in Maven's user settings.
- Docker Desktop running when executing Docker-based integration tests.

The regular Java modules target Java 21. Using JDK 25 to run Maven does
not itself change their configured target version.

Verify the tools:

```powershell
mvn -version
gpg --version
gpg --list-secret-keys --keyid-format LONG
```

When using IntelliJ's Maven runner, check its configured JDK separately:
the runner and an integrated terminal can use different Java installations.

After installing GPG or changing `PATH`, restart IntelliJ so that its
Maven processes inherit the updated environment.

## Credentials and signing keys

Keep credentials and private signing material outside the repository.

Maven reads the Portal credentials from the server entry named `central`
in the user settings file:

```text
Windows: %USERPROFILE%\.m2\settings.xml
```

Example configuration:

```xml

<settings>
    <servers>
        <server>
            <id>central</id>
            <username>PORTAL_TOKEN_USERNAME</username>
            <password>PORTAL_TOKEN_PASSWORD</password>
        </server>
    </servers>
</settings>
```

Merge this entry into an existing settings file rather than replacing
other configuration. Use the credentials generated by the Portal,
not the credentials used to sign in to its website.

Store the signing-key passphrase securely. Local signing uses GnuPG and
its agent; the passphrase must not be placed in the project POM or passed
as a command-line argument.

Maintain a secure backup of the private key and its revocation certificate.

## Version management

The project uses the Maven property `revision` as its central version input.

Supply the release version on the command line:

```text
-Drevision=0.1.0
```

This overrides the development version for that invocation without editing
every module POM. Replace `0.1.0` in the commands below when publishing
another release.

A Maven Central release version must not end in `-SNAPSHOT`.

Published versions are immutable. A correction to a published `0.1.0`
must use a new version, such as `0.1.1`.

## 1. Prepare the source state

Review and commit the changes intended for the release.

```powershell
git status --short
git rev-parse HEAD
```

Record the commit ID. All subsequent release commands must use that same
source state.

Do not commit generated build output, `.flattened-pom.xml`, credentials,
or private signing material.

## 2. Verify the complete project

Start Docker Desktop and run:

```text
mvn -Drevision=0.1.0 clean verify
```

This includes the example modules and IntelliJ plugin checks.

Investigate failures before proceeding. If a test is deliberately disabled,
record the specific test and its reason in the release notes. A successful
build with a disabled test does not establish that the affected feature
works correctly.

Avoid broad test-skipping flags that hide unrelated failures.

## 3. Build and sign the publication artifacts locally

The `release` profile attaches sources and Javadocs and signs the artifacts.

Replace `YOUR_SIGNING_KEY_FINGERPRINT` with the full fingerprint of the
release signing key:

```text
mvn -Prelease -Drevision=0.1.0 -pl vernac-runtime-jdbc,vernac-jdbc-spring-boot-starter,vernac-maven-plugin -am -Dgpg.keyname=YOUR_SIGNING_KEY_FINGERPRINT clean verify
```

The `-am` option includes required reactor projects, including the parent,
runtime, and compiler.

This command does not upload anything.

GnuPG may prompt for the passphrase. No prompt is necessary if the agent
already has it cached.

For each published JAR module, check for:

- The main JAR.
- A `-sources.jar`.
- A `-javadoc.jar`.
- Detached `.asc` signatures for those artifacts and the publication POM.

The parent project publishes a POM and its signature.

The JDBC Spring Boot starter contains no Java classes. Its Javadoc JAR
therefore contains a README explaining its purpose and pointing to the
runtime documentation.

Check the generated `.flattened-pom.xml` files as well:

- Parent coordinates must resolve to the intended release.
- Internal Vernac dependencies must resolve to the same release.
- No internal dependency may unintentionally retain a SNAPSHOT version.

Maven expressions such as `${project.version}` may remain if they resolve
correctly in the published POM. CI-friendly version placeholders must be
resolved appropriately by the flattening step.

## 4. Upload to the Central Publisher Portal

Run the same selected-module build with `deploy`:

```text
mvn -Prelease -Drevision=0.1.0 -pl vernac-runtime-jdbc,vernac-jdbc-spring-boot-starter,vernac-maven-plugin -am -Dgpg.keyname=YOUR_SIGNING_KEY_FINGERPRINT clean deploy
```

This command uploads the release artifacts.

The Central Publishing plugin is configured with:

```xml

<publishingServerId>central</publishingServerId>
<autoPublish>false</autoPublish>
<waitUntil>validated</waitUntil>
```

Consequently, Maven uploads the deployment and waits for validation.
Final publication requires a separate action in the Portal.

Open:

https://central.sonatype.com/publishing/deployments

Record the deployment ID together with the release version and commit ID.

If validation fails, inspect the reported errors and correct the deployment
before publishing. Do not interpret a successful local build as successful
Portal validation.

## 5. Review and publish

Before clicking **Publish**, verify:

- The deployment status is **Validated**.
- All six intended artifact names are present.
- Every component has the intended version.
- No example or IntelliJ plugin artifact is included.

The Portal may show additional component entries with packaging qualifiers,
such as `?type=pom` or `?type=maven-plugin`. Inspect their coordinates rather
than relying solely on the displayed component count.

Validation checks publication requirements. It does not run Vernac's tests
or verify functional correctness.

Click **Publish** and wait for **Published**.

If the status remains **Publishing**, inspect the existing deployment rather
than immediately submitting another deployment of the same version.

## 6. Verify consumption from Maven Central

Verify the release using a standalone consumer project and a fresh local
Maven repository. This prevents artifacts installed during development or
deployment from masking missing remote artifacts.

For example:

1. Copy `templates/vernac-basic` to a temporary directory outside the Vernac
   reactor.
2. Set its `vernac.version` property to the published version.
3. Build it with a new, empty Maven repository directory:

```text
mvn -U -Dmaven.repo.local=C:/temp/vernac-central-check-0.1.0 clean verify
```

Run this command in the standalone project's directory. Choose a different
repository directory if the example path already contains cached artifacts.

Check that the build downloads Vernac artifacts from Maven Central and
successfully generates, compiles, and tests the example.

Verify the JDBC Spring Boot starter separately with a standalone consumer
that declares it as a dependency; the basic template alone does not verify
the starter's dependency graph.

Publication and repository availability may not be simultaneous. If the
new version is not yet available, retry later with `-U`.

This download check must not use a prior local `install` of Vernac into
the fresh repository.

## 7. Record the release in Git

After successful publication and consumption verification, tag the exact
commit used to build the release:

```text
git tag -a maven-v0.1.0 RELEASE_COMMIT_SHA -m "Maven Central release 0.1.0"
git push origin maven-v0.1.0
```

Replace `RELEASE_COMMIT_SHA` with the previously recorded commit ID.
Ensure that commit is also pushed to the repository.

Use `maven-v<version>` for Maven Central release tags and
`plugin-v<version>` for IntelliJ plugin release tags. The existing `v0.1.0`
tag identifies an earlier preview and must not be moved or reused.

Create a GitHub Release for the tag, including:

- A short summary of the release.
- Supported Java and tooling requirements.
- Known limitations and deliberately disabled tests.
- Relevant distribution assets, if prepared separately.

Do not move an existing published release tag to a different commit.

Then advance the root `revision` development default to the next planned
SNAPSHOT version, for example:

```xml

<revision>0.1.1-SNAPSHOT</revision>
```

Commit this development-version change separately.

## IntelliJ plugin distribution

The IntelliJ plugin is released separately from the Maven Central artifacts.
Its ZIP contains the plugin and the bundled language server.

The Marketplace plugin ID is `org.vernac`. Keep it stable across updates.
The Maven module name `vernac-intellij` and Java packages
`org.vernac.intellij` remain unchanged.

### 1. Prepare and build

Commit the intended changes and start with a clean working tree. Record the
source commit before building:

```powershell
git status --short
git rev-parse HEAD
```

Use JDK 25. For a temporary PowerShell configuration, substitute the path of
your installed JDK:

```powershell
$env:JAVA_HOME = "C:\path\to\jdk-25"
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
mvn -version
```

Build from the repository root:

```powershell
$releaseVersion = "0.1.0"
mvn "-Drevision=$releaseVersion" -pl vernac-intellij -am clean verify
```

Continue only after a successful build. The ZIP is located at:

```text
vernac-intellij/target/vernac-intellij-<version>-plugin.zip
```

The command-line revision does not change the development version in the POM.

The current template version injection uses the project version. Check that
the generated project's `vernac.version` references a release available on
Maven Central. With this shared version configuration, publish the matching
Maven artifacts before distributing a new plugin version. Independent plugin
bugfix releases will require separating the plugin version from the template's
Vernac dependency version first.

Do not redeploy an already published Maven version to release a plugin.

### 2. Test the exact ZIP

In IntelliJ IDEA, use **Settings → Plugins → gear menu → Install Plugin from
Disk**. Select the generated ZIP and restart the IDE if requested.

Check:

- The displayed plugin version.
- Syntax highlighting, semantic diagnostics and context-aware completion.
- Go to Declaration for a reference to a Vernac type.
- Project creation with custom group ID, artifact ID and base package.
- Correct packages and Maven coordinates in the generated files.
- The intended Vernac dependency version in the generated POM and README.
- Automatic Maven import of the generated project.
- Successful execution of `./mvnw.cmd clean verify` in the generated project
  on Windows.

The early manually installed plugin used ID `org.vernac.intellij`.
Marketplace rejected that ID because it contains `intellij`. For the one-time
migration, uninstall the old plugin before installing the `org.vernac` build.
Normal updates with the same ID do not require this migration step.

Keep the tested ZIP for both distribution channels. Do not rebuild between
testing and upload; if a rebuild is necessary, test the replacement ZIP.

### 3. Tag the tested commit

Tag the exact commit recorded before the build:

```powershell
git tag -a "plugin-v$releaseVersion" RELEASE_COMMIT_SHA -m "Vernac IntelliJ plugin $releaseVersion"
git push origin "plugin-v$releaseVersion"
```

Replace `RELEASE_COMMIT_SHA` with the recorded commit ID and ensure that the
commit is pushed as well. Do not move an existing published tag.

### 4. Create the GitHub Release

Create a GitHub Release for `plugin-v<version>`, titled **Vernac IntelliJ Plugin <version>**. Attach the tested ZIP.

Include a summary of changes, known limitations and installation instructions.
State compatibility according to the packaged `plugin.xml`; do not promise
support for IDE versions outside its declared range. Mark early previews as
pre-releases where appropriate.

### 5. Submit to JetBrains Marketplace

Sign in at https://plugins.jetbrains.com/.

For the first release, choose **Upload plugin**, select the vendor profile
and upload the tested ZIP. Complete vendor verification in the Marketplace
account; identity documents and banking information do not belong in this
repository.

Use these public project details:

| Field                          | Value                                          |
|--------------------------------|------------------------------------------------|
| License                        | Apache License 2.0                             |
| Source code URL                | https://github.com/DannyReinhold/vernac        |
| Website, where available       | https://vernac.org                             |
| Issue tracker, where available | https://github.com/DannyReinhold/vernac/issues |

Select appropriate language-support tags from the available choices. For
normal public distribution, use the default channel and leave the hidden
flag unchecked. Leave the advertising flag unchecked unless the plugin
actually contains advertising. Describe the preview status in the listing.

For later versions, upload an update to the existing plugin listing.
Do not create another listing or change the plugin ID.

A successful upload starts the review process; it does not establish that
the plugin is approved or publicly available. Monitor the submission and
respond to review feedback. After approval, verify the public listing and
installation through Marketplace, then link the listing from the project
website and documentation.

## Troubleshooting

### GPG cannot be found

If Maven reports `Could not determine gpg version`, check:

```powershell
gpg --version
(Get-Command gpg).Source
```

Restart IntelliJ after changes to `PATH`.

For diagnosis, the executable can be supplied explicitly:

```text
"-Dgpg.executable=C:\path\to\gpg.exe"
```

Do not commit a machine-specific executable path to the project POM.

### Javadoc generation fails

Fix malformed Javadoc comments in the sources.

Use `{@code ...}` for literal code and placeholders containing angle brackets:

```java
/** Generated class name: {@code <EventName>Listener}. */
```

Do not disable all Javadoc validation simply to make the release build pass.

### Docker works, but Testcontainers cannot connect

Check the detailed Testcontainers log, especially the attempted connection
strategies and their underlying exceptions.

A working Docker CLI does not guarantee compatibility between the Docker
Engine API and the Docker client embedded in Testcontainers.

The temporary workaround used with Testcontainers 1.20.4 and Docker 29 was:

```text
vernac-example/src/test/resources/docker-java.properties
```

```properties
api.version=1.44
```

Reassess this workaround when updating Testcontainers. It addresses
connection compatibility, not failures in repository or schema behavior.

### Portal authentication fails

Check that:

- The token has not expired.
- The credentials are the Portal-generated token values.
- The Maven server ID is `central`.
- IntelliJ uses the expected user `settings.xml`.
- The Portal account has access to the `org.vernac` namespace.

Never include token values in issue reports or build-log excerpts.

## GitHub Actions automation

The release workflow is located at `.github/workflows/release.yml` and is
started manually with a release version and a dry-run option.

The successful dry run verified the CI build and signing path. An actual
publication through this workflow is a separate verification step.

The current workflow verifies the project and builds the selected publication
artifacts. In dry-run mode it does not deploy them. In deployment mode it
uploads to the Central Publisher Portal for validation; final publication
remains a manual Portal action.

CI signing uses the Maven GPG plugin's Bouncy Castle signer. Local releases
in this guide use GnuPG. CI credentials and private signing material are
provided through GitHub Actions secrets, never repository files.

After a CI deployment, perform the Portal review, publication and independent
consumer checks described above. Record the workflow's source commit when
creating the release tag.

The workflow does not currently publish the IntelliJ plugin, create release
tags or create GitHub Releases. Those steps remain manual.

Future plugin automation should retain the tested ZIP and use that same
artifact for GitHub Releases and Marketplace. Any Marketplace upload token
must be stored as a secret. Never include credentials, private keys or
passphrases in commands, release notes, screenshots or shared build logs.
