# Bundled offline password corpus

Status: implemented in **0.6.0-SNAPSHOT** in the existing optional
`org.vernac:vernac-saas-identity-spring-security` artifact. This supplies the real
common-password dataset for the [credential primitives](saas-credential-primitives.md).
It does not add registration endpoints, credential persistence or automatic Spring beans.

## What is included

The bundle is a reproducibly curated subset of SecLists' first million xato-net
common-password entries. It contains **10,908 unique passwords of 15–128 Unicode code
points**, after NFC normalization. The other 989,092 source entries are shorter than
the D14 minimum and are already rejected by the length rule. Do not weaken the minimum
to make more short list entries relevant. This particular snapshot has no duplicate
normalized retained entries or oversized retained candidates.

are pinned together. The JAR includes the full upstream notice at
`META-INF/licenses/seclists-MIT.txt` and modification/provenance attribution at
`META-INF/NOTICE-identity-passwords.txt`. Vernac's own code remains Apache-2.0.
No identity associations, username/password pairs or account records are ingested.
The full upstream source is not shipped in the application artifact.

This is a finite common-password baseline, **not the full Have I Been Pwned database**,
not exhaustive detection of compromised secrets, and not a security/compliance guarantee.
The source is historical; a pinned commit/curation date does not prove that the underlying
password observations are recent. An absent password is not thereby known to be safe.

## Explicit use, entirely offline

Inside the trusted authentication implementation, after the applicable admission gates:

```java
var passwords = new CredentialPasswords(OfflinePasswordBlocklist.bundled());
```

The types are in `org.vernac.saas.identity.security.credentials`. Construct/reuse the
service during explicit setup, not once per request. `encode` applies the current
creation policy and this whole-secret list; `matches` continues to verify existing
encodings without retroactive blocklist rejection. There is no automatic login, bean,
module activation or permission grant. Custom reviewed datasets still use the existing
explicit `OfflinePasswordBlocklist.load` entrypoint and its integrity/sanity checks.

`bundled()` reads its bounded versioned manifest and resource from the classpath. It uses
the existing strict loader, verifies the exact resource hash and count, and fails
technically on a missing/corrupt/unsupported bundle. There is no empty-list fallback,
background update or HTTP request. No submitted password/hash is transmitted to a
provider. Never expose the dataset or credential endpoints through a generic resource
handler; the corpus is outside Spring's normal public/static resource locations.

The resource manifest and `curation.json` travel with the JAR. The curation process
preserves significant case/whitespace, normalizes NFC, removes duplicates, filters the
accepted scalar/length/line-format bounds and sorts deterministically by UTF-8 bytes.
It generates LF with a final newline. Repository attributes pin these bytes to LF on
Windows as well; changing line endings changes the resource digest and must fail load.
There is no runtime substring matching or provider-specific normalization.

## Reproduce and update deliberately

The standard-library-only `tools/identity_password_corpus.py` never downloads data.
Download the exact pinned upstream file to a local file using your normal trusted
workflow, then from the repository root run:

```text
python tools/identity_password_corpus.py --upstream /path/to/upstream.txt --check
```

Use the corresponding Windows path when running in PowerShell. The tool validates the
pinned source size/hash and bundled license digest, derives the resources and compares
all generated bytes and provenance statistics. Omitting `--check` rewrites the derived
files. It prints only a status message, not password values. The upstream download is a
maintainer action, not part of application startup, ordinary Maven builds or tests.

For an update, review source quality/scope and upstream licensing first. Change the
commit/path/source digest, corpus version and any changed license pin explicitly; then
regenerate and review entry counts, exclusions, resource digest and the attribution.
Update the distribution assertions and this contract together. Do not download latest
at runtime, silently replace the reviewed source, add synthetic phrases to meet floors
or infer quality from entry count alone. The script's pin is not a publisher signature;
review of the source/manifest in the pull request is the trust boundary.

A new blocklist applies to later password enrollment/change. It does not invalidate
existing credentials or require an aggregate-schema migration by itself. A future change
to password representation/encoding has separate versioned compatibility rules.

## Verification and release boundary

Unit tests load the actual bundle, exercise real long common-password rejection, check
every entry with the Java input policy, and verify an independent test phrase with the
real Spring encoder. Post-package tests inspect the actual JAR's payload, manifest,
provenance and complete license/notice. Offline Python tests verify deterministic
curation vectors and tracked resource/metadata consistency. The full pinned source was
also reproduced locally with `--check`; routine CI needs no upstream network fetch.
CI/release gates require these proofs without skips.

This closes the missing bundled-corpus foundation only. Credentials/challenges/admission
persistence, storage budgets/cleanup, protected mail, provisioning, browser sessions and
complete SaaS UI remain mandatory work. A01/A02 and final full-SaaS/manual acceptance
remain OPEN.
